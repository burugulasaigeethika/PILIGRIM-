================================================================================
1. EXECUTIVE SUMMARY & CORE PHILOSOPHY
================================================================================

PilgrimAI is a local, zero-hallucination, domain-specific AI assistant built for 
pilgrims visiting temples across Telangana, India.

Core Design Principles:
- 100% Offline & Private: Runs using local SentenceTransformers, local Qdrant,
  local BM25, and local Ollama (Qwen 2.5 1.5B).
- Zero Hallucination: The LLM runs at Temperature = 0.0 with strict instructions
  to answer ONLY from retrieved facts.
- Parent-Child Chunking: Searches small 300-character snippets for high precision,
  but delivers full section context to the LLM.
- Hybrid Search + Neural Reranking: Combines Dense Vectors + BM25 Keywords via
  Reciprocal Rank Fusion (RRF), then filters the best Top-3 with a Cross-Encoder.
- Relevance Guardrail: Rejects out-of-domain questions before LLM generation if
  the reranking score is below -3.0.


================================================================================
2. HIGH-LEVEL PIPELINE FLOW (STEP-BY-STEP)
================================================================================

PHASE 1: OFFLINE INGESTION (Run once to build search databases)
  1. loader.py scans dataset folders and reads all JSON files.
  2. parser.py converts JSON trees into clean, structured Parent Documents.
  3. chunker.py splits Parent Documents into 300-char Child Chunks with IDs.
  4. embeddings.py converts Child Chunks into 384-dimensional dense vectors.
  5. vectordb.py saves vectors and metadata into local Qdrant database.
  6. bm25.py indexes Child Chunks into an in-memory sparse keyword index.
  7. knowledge_registry.py loads full raw documents into an in-memory cache.

PHASE 2: ONLINE QUERY EXECUTION (Runs on every user message)
  1. User asks a question (e.g. "What are the darshan timings at Yadagirigutta?").
  2. query_planner.py identifies temple names, categories, and assigns 1 of 5 routes.
  3. vectordb.py finds Top-30 semantic vector matches.
  4. bm25.py finds Top-30 exact keyword matches.
  5. rrf.py (Reciprocal Rank Fusion) merges and deduplicates both lists.
  6. reranker.py (Cross-Encoder) evaluates query-chunk pairs and picks Top-3.
  7. guardrail.py checks if top score >= -3.0. If not, returns polite refusal.
  8. completeness_validator.py checks whether facts are confirmed or missing.
  9. context_builder.py formats the top parent documents into clean Markdown.
  10. answer_scope_controller.py wraps context with multi-part question rules.
  11. prompt.py constructs the anti-hallucination system prompt.
  12. llm.py sends prompt to local Ollama (Qwen 2.5 1.5B @ temperature=0.0).
  13. answer_grounding_validator.py checks generated text against source facts.
  14. chat.py returns the verified answer with exact source citations.


================================================================================
3. THE 5 SMART RETRIEVAL ROUTES
================================================================================

1. TARGETED ROUTE
   - Trigger: Single temple + specific category (e.g., "VIP darshan at Yadagirigutta").
   - Action: Hybrid search filtered strictly by temple name.

2. COMPLETE_CATEGORY ROUTE
   - Trigger: Exact category query (e.g., "Dress code for Bhadrachalam").
   - Action: Instant O(1) direct lookup from knowledge_registry.py memory cache.

3. CROSS_TEMPLE ROUTE
   - Trigger: Mentions 2 or more temples (e.g., "Compare accommodation in Vemulawada vs Yadagirigutta").
   - Action: Retrieves facts for each temple independently and merges them side-by-side.

4. MULTI_CATEGORY ROUTE
   - Trigger: Single temple + 2 or more distinct questions (e.g., "Timings, entry fees, and parking for Ramappa").
   - Action: Slices context for each requested topic to ensure no question is skipped.

5. BROAD_TEMPLE ROUTE
   - Trigger: General overview question (e.g., "Tell me about Thousand Pillar Temple").
   - Action: Retrieves high-level sections in priority order (History -> Deity -> Timings -> Festivals).

5. TOP 5 INTERVIEW / VIVA QUESTIONS & MODEL ANSWERS
================================================================================

Q1: Why did you choose Parent-Child Chunking instead of standard fixed chunking?
Answer: Fixed chunking creates arbitrary cuts that often separate related data
(like pooja ticket prices from pooja names). With Parent-Child Chunking, we search
over small 300-character child chunks for high semantic precision, but inject the
entire parent document into the prompt so the LLM has complete context.

Q2: Why combine Dense Vector Search and BM25 Sparse Search using RRF?
Answer: Dense vector embeddings understand high-level semantics (e.g., "where to stay"
-> accommodation), but can struggle with exact proper nouns and numbers. BM25
excels at exact keyword and numeric matching (e.g., "Saswatha Pooja ₹500").
Reciprocal Rank Fusion (RRF) merges their strengths without needing manual score tuning.

Q3: Why is Temperature set to 0.0 in the LLM?
Answer: PilgrimAI is an informative pilgrimage assistant where precision is vital.
A temperature of 0.0 turns off stochastic creativity, ensuring the model deterministically
selects the most probable tokens strictly grounded in the retrieved facts.

Q4: How does your pipeline block out-of-domain queries without wasting LLM tokens?
Answer: guardrail.py checks the top score from the neural Cross-Encoder. If the score
is below -3.0, the query is identified as irrelevant (e.g., general trivia or coding)
and an instant refusal message is returned immediately without invoking the LLM.

Q5: What is the Tri-State Completeness Principle in completeness_validator.py?
Answer: In travel and accessibility, missing data must never be reported as confirmed
absence. The validator distinguishes between:
1. Confirmed Available (affirmative evidence in text)
2. Confirmed Unavailable (explicit negative statements like "No lift")
3. Information Not Available (missing data), avoiding misleading claims.
